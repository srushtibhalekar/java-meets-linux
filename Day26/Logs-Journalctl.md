# 1. What Are Logs?

A **log** is a record of events generated by a system, application, service, or user action.

For example:

```text
Application started
User logged in
Database connection established
File not found
Permission denied
Server stopped
```

Logs help us understand:

> What happened?

and:

> When did it happen?

and:

> Why did it happen?

---

# 2. Why Are Logs Important?

Logs are extremely important for:

* Troubleshooting
* Debugging
* Security
* Monitoring
* Auditing
* Application development
* Server administration

Example:

A Java application suddenly stops working.

Instead of guessing, you can inspect:

```text
Application logs
        ↓
Exception
        ↓
Error message
        ↓
Root cause
        ↓
Fix
```

# 3. Common Linux Log Locations

Traditional Linux logs are often stored under:

```text
/var/log/
```

Check:

```bash
ls /var/log
```

You may see files/directories such as:

```text
auth.log
syslog
kern.log
boot.log
journal/
```

The exact files vary by Linux distribution and logging configuration.

---

# 4. Explore `/var/log`

Run:

```bash
cd /var/log
```

Then:

```bash
ls
```

For detailed information:

```bash
ls -lh
```

Check directories:

```bash
ls -ld */
```

---

# 5. Check Log File Types

Use:

```bash
file /var/log/*
```

Some entries may be directories, text logs, binary files, or compressed files.

---

# 6. Viewing Logs With `cat`

For a small log:

```bash
cat /var/log/some-log-file
```

However, large logs should usually be viewed using:

```bash
less
```

---

# 7. Using `less`

Example:

```bash
less /var/log/some-log-file
```

Useful keys:

```text
Space       Next page
b           Previous page
/word       Search
n           Next match
N           Previous match
q           Quit
```

---

# 8. Viewing the Last Lines

Use:

```bash
tail /var/log/some-log-file
```

By default, `tail` shows the last 10 lines.

Use:

```bash
tail -n 50 /var/log/some-log-file
```

to show the last 50 lines.

---

# 9. Follow Logs in Real Time

Use:

```bash
tail -f application.log
```

This keeps the terminal open and displays new lines as they are added.

Very useful for:

* Application logs
* Web server logs
* Java logs
* Deployment logs

Stop with:

```text
Ctrl + C
```

---

# 10. `tail -F`

You may also see:

```bash
tail -F application.log
```

`-F` is useful when a log file is rotated or recreated.

---

# 11. Search Logs With `grep`

Example:

```bash
grep "ERROR" application.log
```

Case-insensitive:

```bash
grep -i "error" application.log
```

With line numbers:

```bash
grep -in "error" application.log
```

---

# 12. Count Errors

```bash
grep -ic "error" application.log
```

Example output:

```text
15
```

Meaning 15 matching lines were found.

---

# 13. Search Multiple Error Types

```bash
grep -Ei "error|exception|failed|fatal" application.log
```

This is useful for application troubleshooting.

---

# 14. Search Warnings

```bash
grep -i "warning" application.log
```

Or:

```bash
grep -Ei "warning|warn" application.log
```

# 15. What Is `systemd`?

Modern Linux systems often use **systemd** to manage:

* Services
* Processes
* Boot
* System state
* Logging

Its logging component is commonly called the **systemd journal**.

The command used to inspect the journal is:

```bash
journalctl
```

---

# 16. What Is `journalctl`?

`journalctl` is used to query logs collected by the systemd journal.

Basic command:

```bash
journalctl
```

This can display a large amount of information.

Use:

```bash
journalctl --no-pager
```

to print the output without opening a pager.

---

# 17. View Recent Journal Entries

Use:

```bash
journalctl -n
```

This shows recent entries.

For example:

```bash
journalctl -n 20
```

shows approximately the last 20 entries.

---

# 18. Follow the Journal in Real Time

Use:

```bash
journalctl -f
```

This works similarly to:

```bash
tail -f
```

New journal entries will appear as they are generated.

Stop with:

```text
Ctrl + C
```

---

# 19. Show Logs From the Current Boot

Use:

```bash
journalctl -b
```

This displays journal entries from the current boot.

This is useful when troubleshooting something that happened after the system started.

---

# 20. Previous Boot Logs

Depending on whether previous boot journals are retained, you can inspect earlier boots.

List boots:

```bash
journalctl --list-boots
```

Example:

```text
-2 ...
-1 ...
 0 ...
```

Current boot is commonly represented by:

```text
0
```

Then:

```bash
journalctl -b -1
```

can show logs from the previous boot if those logs are available.

---

# 21. Boot Troubleshooting

If a system behaved incorrectly after startup, try:

```bash
journalctl -b
```

Search errors:

```bash
journalctl -b | grep -i error
```

Or:

```bash
journalctl -b -p err
```

---

# 22. Filter by Priority

Journal entries have priorities.

Common levels include:

```text
0 = emergency
1 = alert
2 = critical
3 = error
4 = warning
5 = notice
6 = informational
7 = debug
```

You can filter with:

```bash
journalctl -p err
```

This displays error-level messages.

---

# 23. Show Errors and More Severe Messages

Use:

```bash
journalctl -p err..emerg
```

This requests entries from error through emergency severity.

---

# 24. Show Warnings and Errors

```bash
journalctl -p warning..emerg
```

This can help identify important system events.

---

# 25. Logs From a Specific Service

This is one of the most useful commands.

Syntax:

```bash
journalctl -u service-name
```

Example:

```bash
journalctl -u ssh
```

Some distributions use:

```bash
journalctl -u sshd
```

for the SSH service.

---

# 26. Follow Service Logs

Use:

```bash
journalctl -u ssh -f
```

This continuously displays new logs for that service.

---

# 27. Recent Service Logs

Use:

```bash
journalctl -u ssh -n 50
```

This shows recent entries for the service.

Replace `ssh` with the actual service name on your system.

---

# 28. Java Service Example

# 37. Kernel Logs

The kernel also produces logs.

A common command is:

```bash
dmesg
```

View the latest messages:

```bash
dmesg | tail
```

Search for errors:

```bash
dmesg | grep -i error
```

Search for hardware-related messages:

```bash
dmesg | grep -Ei "usb|disk|network|memory"
```

Depending on system configuration, some `dmesg` output may require elevated privileges.

---

# 38. Kernel Logs Through `journalctl`

You can also use:

```bash
journalctl -k
```

This displays kernel messages stored in the journal.

Follow:

```bash
journalctl -k -f
```

# 39. Authentication Logs

Authentication-related events may be recorded in distribution-specific files.

On Debian/Ubuntu systems, you may commonly find:

```text
/var/log/auth.log
```

On many RHEL/Fedora-based systems, authentication messages are commonly found in:

```text
/var/log/secure
```

Check the files available on your system:

```bash
ls /var/log
```

---

# 40. Searching Authentication Logs

On a system using `/var/log/auth.log`:

```bash
sudo grep -i "failed" /var/log/auth.log
```

Successful authentication:

```bash
sudo grep -i "accepted" /var/log/auth.log
```

The exact log format depends on the system.

---

# 41. `sudo` Logs

You may find sudo-related activity in authentication logs.

For example:

```bash
sudo grep -i "sudo" /var/log/auth.log
```

This can help administrators understand privileged command activity.

```bash
sudo less /var/log/syslog
```

Search:

# 43. Log Rotation

Logs can become very large.

Linux systems commonly use **log rotation** to:

* Rotate old logs
* Compress old logs
* Limit disk usage
* Retain logs for a period
* Create new active log files

A common utility is:

```bash
logrotate
```

Check whether it is available:

```bash
command -v logrotate
```

---

# 44. Why Log Rotation Matters

Imagine:

```text
application.log
```

grows continuously:

```text
100 MB
500 MB
1 GB
5 GB
20 GB
```

Eventually it can consume significant disk space.

Log rotation helps control this.

---

# 45. Compressed Logs

Rotated logs may be compressed.

You might see:

```text
application.log
application.log.1
application.log.2.gz
```

To inspect a gzip-compressed log:

```bash
zcat application.log.2.gz
```

Search it:

```bash
zgrep -i "error" application.log.2.gz
```

# 50. Search With Context

Sometimes the error line alone is not enough.

Use:

```bash
grep -i -C 3 "error" application.log
```

`-C 3` means:

> Show 3 lines before and after the matching line.

You can also use:

```bash
grep -i -B 3 "error" application.log
```

for lines before, or:

```bash
grep -i -A 3 "error" application.log
```

for lines after.

---

You can combine journal output with other commands:

```bash
journalctl -u my-java-app --no-pager | grep -Ei "error|exception"
```

Count errors:

```bash
journalctl -u my-java-app --no-pager | grep -ic "error"
```

# 62. Basic Log Analyzer

Create:

```bash
nano log-analyzer.sh
```

Add:

```bash
#!/bin/bash

if [ "$#" -ne 1 ]; then
    echo "Usage: $0 logfile"
    exit 1
fi

LOG_FILE="$1"

if [ ! -f "$LOG_FILE" ]; then
    echo "Log file not found: $LOG_FILE"
    exit 1
fi

echo "================================"
echo "        LOG ANALYZER"
echo "================================"

echo
echo "Log File:"
echo "$LOG_FILE"

echo
echo "Total Lines:"
wc -l "$LOG_FILE"

echo
echo "Errors:"
grep -ic "error" "$LOG_FILE"

echo
echo "Warnings:"
grep -ic "warning" "$LOG_FILE"

echo
echo "Exceptions:"
grep -ic "exception" "$LOG_FILE"

echo
echo "Last 20 Lines:"
tail -n 20 "$LOG_FILE"
```

# ⚠️ 69. Common Mistakes

### Mistake 1 — Reading huge logs with `cat`

Avoid:

```bash
cat huge.log
```

Prefer:

```bash
less huge.log
```

or:

```bash
tail -n 100 huge.log
```

---

### Mistake 2 — Searching without permissions

You may see:

```text
Permission denied
```

Use appropriate privileges when you are authorized:

```bash
sudo grep -i "error" /var/log/file
```

---

### Mistake 3 — Assuming the same log files exist everywhere

For example:

```text
/var/log/syslog
```

may not exist on every Linux distribution.

Always inspect:

```bash
ls /var/log
```

---

### Mistake 4 — Assuming the service name

SSH may be:

```text
ssh
```

or:

```text
sshd
```

Check:

```bash
systemctl list-units --type=service
```

---

### Mistake 5 — Forgetting time filters

Huge journal output can be difficult to analyze.

Instead of:

```bash
journalctl
```

use:

```bash
journalctl --since "1 hour ago"
```

# 🔍 70. Troubleshooting Checklist

When an application fails:

```text
1. Is the service running?
2. When did the problem start?
3. What does the recent log show?
4. Are there ERROR messages?
5. Are there exceptions?
6. Is the database reachable?
7. Is the port available?
8. Is disk space available?
9. Did the application restart?
10. Do new logs confirm the fix?
```

Useful commands:

```bash
systemctl status SERVICE
```

```bash
journalctl -u SERVICE -n 100
```

```bash
journalctl -u SERVICE -p err
```

